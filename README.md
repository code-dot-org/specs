# Specs

Specs for Code.org software. A spec here is written before the code, and is
what a coding agent is given to work from. No application code lives in this
repo.

This repo currently supports two frameworks, and can be extended to support more.

| Track    | Directory   | Use it when                                                                                    |
| -------- | ----------- | ---------------------------------------------------------------------------------------------- |
| OpenSpec | `openspec/` | you want a structured proposal, design and task list, and a running record of current behavior |
| Freeform | `freeform/` | you want one markdown file, shaped however the work needs                                      |

## Layout

```
openspec/          OpenSpec specs and changes
.openspec-store/   marks this repo as the OpenSpec store named specs
freeform/          plain markdown specs
AGENTS.md          rules for agents working in this repo
.agents/ .claude/  agent skills and commands generated by `openspec init`
```

## Rules for both tracks

1. Write a spec in one place: either `openspec/` or `freeform/`, not
   both.
2. Every spec names the code repo or repos it targets.
3. Keep the status up to date. Freeform: the `status` field. OpenSpec: archive
   the change when the code ships.

## Working with a code repo

Clone this repo next to the code repo. The agent needs to read the spec and
edit the code in one session, so it needs access to both checkouts. With
Claude Code, from the code repo:

```
claude --add-dir ../specs
```

Spec edits are committed here. Code edits are committed in the code repo.

## Freeform track

1. Copy `freeform/TEMPLATE.md` to `freeform/<slug>.md`. Use a lowercase,
   hyphenated slug that says which system it is about, such as
   `dashboard-section-export.md`. If the spec needs diagrams or supporting
   notes, make it a directory: `freeform/<slug>/spec.md`.
2. Set the three fields at the top of the file: `status`, `owner` and
   `repos`.
3. Work on the file with your agent until it says what you intend to build.
4. Commit it here, then point the agent at it from the code repo.
5. Update `status` as the work moves.

Those three fields are the only required part of the file. Example:

```yaml
---
status: draft
owner: <your GitHub username>
repos: [code-dot-org]
---
```

- `status`: where the spec stands; one of the values in the table below.
- `owner`: the person to ask about the spec.
- `repos`: the code repos the spec will change, as a comma-separated list
  in square brackets. Keep the brackets when there is only one repo:
  `[code-dot-org]`, or `[code-dot-org, infrastructure]` for two.

| Status        | Meaning                                             |
| ------------- | --------------------------------------------------- |
| `draft`       | still changing; do not build from it yet            |
| `accepted`    | agreed; being built or ready to build               |
| `implemented` | the code has shipped                                |
| `superseded`  | replaced; say by what in the first line of the body |

The headings in the template are suggestions. Delete or replace them.

A freeform spec may be turned into an OpenSpec change at any point. This is
never required. When it happens, delete the freeform copy.

## OpenSpec track

This repo is an [OpenSpec store](https://openspec.dev/docs/stores): the
`openspec/` tree lives here, and OpenSpec commands run in a code repo read
and write it.

### Once per machine

1. Install an OpenSpec release that has the `openspec store` command. The
   npm install needs Node 22.20.0 or newer:

   ```
   npm install -g @fission-ai/openspec@latest
   ```

2. Clone this repo.
3. Register the clone as a store, then check it:

   ```
   openspec store register <path to your clone>
   openspec store doctor specs
   ```

A machine can register only one checkout under the name `specs`.

### Once per code repo

The code repo holds a single file, `openspec/config.yaml`:

```yaml
store: specs
```

OpenSpec ignores this line, with a warning, if the code repo's `openspec/`
also contains `specs/` or `changes/`. Move those here first.

### The loop

Run these from the code repo. OpenSpec prints
`Using OpenSpec root: specs` when it has resolved the store.

| Step    | Claude Code     | What it does                                                                           |
| ------- | --------------- | -------------------------------------------------------------------------------------- |
| Explore | `/opsx:explore` | think a problem through before proposing anything                                      |
| Propose | `/opsx:propose` | create `openspec/changes/<change>/` with a proposal, design, spec deltas and tasks     |
| Apply   | `/opsx:apply`   | work through the tasks in the code repo                                                |
| Archive | `/opsx:archive` | merge the spec deltas into `openspec/specs/` and move the change to `changes/archive/` |

`openspec list`, `openspec status` and `openspec validate` report on changes
from the command line.

### What a store does not do

- **It does not sync.** OpenSpec never runs `git pull` or `git push` here.
  Pull this repo before you start. A new change exists only in your checkout
  until you commit and push it.
- **It does not separate code repos.** There are no per-repo folders, and
  nested change directories are refused. Put the system in the name:
  `dashboard-classlink-rostering`, not `classlink-rostering`.
