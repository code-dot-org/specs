# Specs

Specs for CodeAI software. A spec here is written before the code, and is
what a coding agent is given to work from. No application code lives in this
repo.

This repo currently supports two frameworks (tracks), and can be extended to support more.

| Track    | Directory   | Use it when                                                                                    |
| -------- | ----------- | ---------------------------------------------------------------------------------------------- |
| OpenSpec | `openspec/` | you want a structured proposal, design and task list, and a running record of current behavior |
| Freeform | `freeform/` | you want one markdown file, shaped however the work needs                                      |

## Layout

```
openspec/          OpenSpec specs and changes
.openspec-store/   marks this repo as the OpenSpec store named specs
freeform/          plain markdown specs
AGENTS.md          rules for agents working in this repo
.agents/ .claude/  agent skills generated by `openspec init`
.nvmrc             the Node version OpenSpec needs
```

## Rules for both tracks

1. Write a spec in one place: either `openspec/` or `freeform/`, not
   both.
2. Every spec names the code repo or repos it targets.
3. Keep the status up to date. Freeform: the `status` field. OpenSpec: archive
   the change when the code ships.

## Where to work

Start your agent in this repo, both to write a spec and to implement from
one. Add each code repo the spec targets, so the agent can read and edit the
code in the same session. Clone this repo next to the code repos.

With Claude Code:

```
cd specs
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../code-dot-org
```

Repeat `--add-dir` for a spec that targets more than one repo.

What an added repo brings with it in Claude Code:

- Its skills, commands and subagents load automatically.
- Its `CLAUDE.md` loads only because of the environment variable above.
  Without it, the agent does not see that repo's instructions.
- Its permission settings and hooks do not load. If the work depends on
  them, start the agent in the code repo instead; see
  [Running OpenSpec from a code repo](#running-openspec-from-a-code-repo).

Other agents have their own way to open a second directory.

Spec edits are committed here. Code edits are committed in the code repo.

## Freeform track

1. Copy `freeform/TEMPLATE.md` to `freeform/<slug>.md`. Use a lowercase,
   hyphenated slug that says which system it is about, such as
   `dashboard-section-export.md`. If the spec needs diagrams or supporting
   notes, make it a directory: `freeform/<slug>/spec.md`.
2. Set the three fields at the top of the file: `status`, `owner` and
   `repos`.
3. Work on the file with your agent until it says what you intend to build.
4. Commit it here. To implement, tell the agent which spec to build from.
5. Update `status` as the work moves.

Those three fields are the only required part of the file. Example:

```yaml
---
status: draft
owner: <your GitHub username>
repos: [code-dot-org]
---
```

- `status`: where the spec stands; one of the values in the table below.
- `owner`: the person to ask about the spec.
- `repos`: the code repos the spec will change, as a comma-separated list
  in square brackets. Keep the brackets when there is only one repo:
  `[code-dot-org]`, or `[code-dot-org, infrastructure]` for two.

| Status        | Meaning                                             |
| ------------- | --------------------------------------------------- |
| `draft`       | still changing; do not build from it yet            |
| `accepted`    | agreed; being built or ready to build               |
| `implemented` | the code has shipped                                |
| `superseded`  | replaced; say by what in the first line of the body |

The headings in the template are suggestions. Delete or replace them.

A freeform spec may be turned into an OpenSpec change at any point. This is
never required. When it happens, delete the freeform copy.

## OpenSpec track

The `openspec/` directory lives here, and OpenSpec commands are run here.

### Once per machine

In your clone of this repo:

```
nvm install
npm install -g @fission-ai/openspec@latest
openspec --version
```

`nvm install` reads `.nvmrc` and installs Node 22. OpenSpec's npm package
needs Node 22.20.0 or newer. The version printed should be 2.1.0 or newer.

nvm keeps global packages separately for each Node version, so `openspec`
exists only in a shell that is using Node 22. Run `nvm use` in this repo
before you start.

### The loop

Each step is a skill. In Claude Code, type its name after a slash.

| Step    | Skill                      | What it does                                                                           |
| ------- | -------------------------- | -------------------------------------------------------------------------------------- |
| Explore | `/openspec-explore`        | think a problem through before proposing anything                                      |
| Propose | `/openspec-propose`        | create `openspec/changes/<change>/` with a proposal, design, spec deltas and tasks     |
| Apply   | `/openspec-apply-change`   | work through the tasks, editing code in the added code repo                            |
| Sync    | `/openspec-sync-specs`     | merge the spec deltas into `openspec/specs/` without archiving the change              |
| Archive | `/openspec-archive-change` | merge the spec deltas into `openspec/specs/` and move the change to `changes/archive/` |

`openspec list`, `openspec status` and `openspec validate` report on changes
from the command line.

Changes and specs for every code repo share one flat list. There are no
per-repo folders, and nested change directories are refused. Put the system
in the name: `dashboard-classlink-rostering`, not `classlink-rostering`.

### Running OpenSpec from a code repo

This repo is also an [OpenSpec store](https://openspec.dev/docs/stores)
named `specs`. A store lets OpenSpec commands run in a code repo read and
write the `openspec/` directory here. Use it only if you need to start your
agent in the code repo.

1. Make `openspec` available in the code repo's shell. The npm package needs
   Node 22.20.0 or newer, so a repo pinned to an older Node, as
   `code-dot-org` is to Node 20, needs OpenSpec installed another way; see
   the [installation docs](https://openspec.dev/docs/installation).
2. Register your clone of this repo as a store, then check it:

   ```
   openspec store register <path to your clone>
   openspec store doctor specs
   ```

   A machine can register only one checkout under the name `specs`.

3. Give the code repo a single file, `openspec/config.yaml`:

   ```yaml
   store: specs
   ```

   OpenSpec ignores this line, with a warning, if the code repo's
   `openspec/` also contains `specs/` or `changes/`. Move those here first.

OpenSpec prints `Using OpenSpec root: specs` when it has resolved the store.

A store does not sync. OpenSpec never runs `git pull` or `git push` here.
Pull this repo before you start; a new change exists only in your checkout
until you commit and push it.
